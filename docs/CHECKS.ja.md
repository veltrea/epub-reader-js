# 検査のマニュアル

English: [CHECKS.md](CHECKS.md)

```bash
./scripts/check.sh
```

これで 7 つの検査がまとめて走ります。CI からも同じものが走ります。
1 つでも失敗すると、最後に赤い字で「検査に失敗があります」と出て終わります。

**ここに入れてよいのは、人に聞かなくても正解が一意に決まるものだけです。**
判断が要るもの（設計の是非・何を公開するか・ライセンスの選択）は入れません。
警告が出るたびに人を止めることになり、結局その警告が読まれなくなるからです。

**検査は「間違いを責めるもの」ではなく「次にやることを教えるもの」です。**
どの検査も、止まるときに何をすればよいかを出します。言われたとおりに直せば済みます。

---

## 1. ロジックのユニットテスト

```bash
node tests/logic.test.mjs
```

**何を試すか。** 画面を作らずに動かせる処理だけを試します。かなの変換、五十音の分類、
読み上げ辞書の置き換え、綴じ方向の切り替え、組版の補正、自動ページ送り、
スリープタイマー、対訳。162 件あります（2026-08-30 時点）。

**なぜ画面を作らないか。** 画面を作ると、本も音声エンジンも要ります。遅くて、
壊れやすくて、何が原因で失敗したのか分からなくなります。処理を画面から切り離しておけば、
その処理だけを直接呼んで確かめられます。

**止まったとき。** 失敗したテストの名前と、期待した値・実際の値が出ます。
処理を直すか、テストの方が古いならテストを直します。

**機能を足したとき。** 画面を触らない処理を書いたら、ここにテストを足します。
**書ける形にしておくこと自体が大事です。** 画面の中に処理を埋め込むと、
テストが書けません。純粋な関数として切り出しておきます。

---

## 2. メニューの配線（無反応な項目）

```bash
node scripts/check-menu-wiring.mjs
```

**何を見るか。** メニューに項目があるのに、押しても何も起きない状態を見つけます。

**なぜ要るか。** この穴は目で見ても分かりません。メニューは組み上がり、押しても
エラーも出ず、ただ黙っています。**配布版でいちばん目立つ種類の不具合です。**

**判定のしかた。** `src-tauri/src/menu.rs` が出す項目の id を全部集めます。
そのうち、その画面で押せる状態（有効）になるものが、その画面の処理の一覧に無ければ穴です。

| menu.rs の書き方 | 処理が要る場所 |
|---|---|
| `enabled: true` | 本を読む画面と書棚の画面の**両方** |
| `enabled: reader` | 本を読む画面だけ |
| `enabled: shelf` | 書棚の画面だけ |
| それ以外の条件（書き出しの可否など） | どちらにも無ければ警告 |

**止まったとき。** `reader.js` / `shelf.js` の処理の一覧に、その id の処理を書きます。
片方の画面でしか意味がない項目なら、`menu.rs` の `enabled` に `reader` か `shelf` を
渡して、もう片方では淡色にします。**黙って無反応にしないこと。**

## 3. 画面に出る文字列の直書き

```bash
node scripts/check-ui-strings.mjs
```

**何を見るか。** 日本語の文字を、言語ファイルを通さずコードに直接書いていないかを見ます。

**なぜ「日本語があるか」で探さないか。** かなの処理や文の分け方には、日本語の文字が
正当に出てきます（五十音の表、句読点）。「日本語があるか」で探すと誤検出だらけになり、
誰も見なくなります。代わりに **画面へ文字を流し込む所だけ**を見ます。

過去に漏れた 2 件は、どちらもこの形でした。

```
ui-modals.js   alert('再生に失敗しました: ' + e)
dnd.js         el.textContent = '本をここにドロップ'
```

**止まったとき。** `src/locales/ja.json` と `en.json` の**両方**にキーを足して、
`t('キー')` で呼びます。**片方だけだと Rust のテストが失敗します**（キーの集合が
そろっていないため）。

## 4. 設定・版番号・秘匿パス

```bash
node scripts/check-config.mjs
```

**何を見るか。** 5 つです。

| 見るもの | 中身 |
|---|---|
| 版番号 | 2 か所（`src-tauri/tauri.conf.json` と `src-tauri/Cargo.toml`）で一致しているか |
| ビルド番号 | 配布物を作るたびに進む番号が、版番号と組になっているか |
| 安全のための決まり（CSP） | 設定ファイルの側にあるか（HTML に埋め込んでいないか） |
| 秘匿しておきたいパス | git に追跡されていないか |
| 文字のファイル | 中に NUL（文字として存在しない値）が混ざっていないか |

最後に、マニュアルに出てこないメニュー項目があれば警告します（これは止めません）。

**止まったとき。** 出た項目をそのまま直します。どれも正解が 1 つに決まります。

## 5. 機能の記録（文書に書く対象の洗い出し）

```bash
node scripts/feature-inventory.mjs          # 記録と食い違っていないか見る
node scripts/feature-inventory.mjs --write  # 記録を更新する
```

**何を見るか。** コードから機能の一覧を機械的に取り出して、`docs/feature-inventory.json`
と突き合わせます。取り出すのは、メニューの id、設定のキー、テストバスの命令、
対応する拡張子、バックエンドの命令です。

**なぜ AI に読ませて数えないか。** 機能の一覧は推測して作るものではありません。
コードに既に宣言されています。抜き出すのは機械の仕事で、差分は git が取ります。
**文章を書くところだけ人（または AI）がやればよく、毎回全部を読ませる必要はありません。**

**止まったとき。** 出た差分が、そのまま「文書に書く対象」です。

1. 増えた項目をマニュアル（大きい機能なら README も）に書く
2. `node scripts/feature-inventory.mjs --write` で記録を更新する

**順番が大事です。** 先に `--write` すると、書く対象が消えます。

## 6. 記号の突き合わせ（実装と文書の食い違い）

```bash
node scripts/check-symbols.mjs         # 食い違いがあれば止まる
node scripts/check-symbols.mjs --soft  # 数だけ出して止めない（移行中に使う）
```

**何を見るか。** 実装と文書を、集合の引き算で 4 通り比べます。

| 比べ方 | 破れると分かること |
|---|---|
| コードのグループ ⊆ 文書のグループ | 節ごと説明が無い |
| コードの機能 ⊆ 文書の印 | その機能の説明が無い |
| 文書の印 ⊆ コードの機能 | 実装の無い説明が残っている |
| 日本語版の印 = 英語版の印 | 片方の言語だけ書いた |

文書側の「印」は、マニュアルの中に `<!-- menu:xxx -->` の形で埋め込みます。
見えない印なので、読む人の邪魔になりません。

**止まったとき。** 印の無い機能があれば、マニュアルの説明に印を付けます。
実装の無い説明が残っていれば、その説明を消します。

**緑になっても「できている」ではありません。** 分かるのは「同じ名前がどこかに 1 回は
出てくる」だけです。説明の量も、正しさも、画面の見た目も範囲外です。最後は目で見ます。

## 7. 文書に書いた画面の文字が実物と合うか

```bash
node scripts/check-manual-labels.mjs
```

**何を見るか。** 文書が引用している画面の文字が、実際に画面へ出るものと合っているかを
見ます。比べる相手は `src/locales/ja.json` です（画面に出る文字は全部そこにあります。
コードへの直書きは検査 3 が禁じています）。

**なぜ要るか。** マニュアルは Swift 版の試作品を叩き台にして書きました。そのため
試作品のころの名前が残ります。2026-08-30 に 11 か所見つかりました。

| 文書の書き方 | 実際の画面 |
|---|---|
| EpubReaderSpike | epub-reader |
| 環境設定… | 設定… |
| オーディオを書き出し… | この章を音声ファイルに保存… |
| 移動 > しおりを開く | 移動 > しおり |
| 任意の比率… | 自由入力 |

**人が読み比べても気づけません。** 文とアプリを並べて 1 つずつ突き合わせる作業だからです。

**見るのは 2 つの形だけです。**

| 形 | 例 |
|---|---|
| 「…」で終わる語 | `読み上げ辞書を編集…` |
| 「メニュー名 > 項目」の形 | `移動 > 現在地をしおり` |

説明の言い回し（`自動／縦書き／横書き` など）は見ません。**網を狭くする方を選んでいます。**
警告が多いと読まれなくなるからです。

**日本語の文書だけが対象です。** 英語は「…」を文の省略に使うので、この見分け方が
働きません（`Open the engine…` を項目名と取り違えます）。

**止まったとき。** 引用した文字を、`ja.json` にあるものと同じにします。
**画面の側が正しくないなら、そちらを先に直します。**

## 検査が邪魔になったとき

**まず「検査が間違っているのか、実装が間違っているのか」を決めます。**
実装の方が新しいなら、実装が正です。文書や記録の側を直します。

網から外したいものが出たときは、**その検査の除外の一覧に足して、理由をその場に書きます。**
理由の無い除外は、次に読む人が消せません。

検査そのものが役に立たなくなったら消してよいです。ただし**消した理由をコミットに書く**
こと。「うるさいから」は理由になりません。うるさいのは、網が広すぎるか、実装が
実際に食い違っているかのどちらかです。

## 検査を新しく足すとき

足す前に 2 つ確かめます。

1. **正解が一意に決まるか。** 人によって答えが変わるものは入れません。
2. **目で見て気づけるか。** 目で気づけるものは、検査にしなくても直ります。
   検査が要るのは、**目では絶対に気づけないもの**です（無反応なメニュー項目、
   試作品の名前の残り、片方の言語だけの翻訳）。

足したら、**わざと間違えて、本当に止まるかを確かめます。** 止まらない検査は、
あっても無くても同じです。
